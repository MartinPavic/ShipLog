# GitLab Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking.

**Goal:** Add GitLab.com and one self-managed GitLab instance per workspace, while preserving GitHub-only projects and supporting mixed-provider reports.

**Architecture:** Keep GitHub routes, storage, and API adapter intact. Add GitLab workspace OAuth configuration and per-member OAuth connections, then provider-tag project repositories with missing provider defaulting to GitHub. Both provider adapters normalize into the current `Activity` contract before generation.

**Tech Stack:** Next.js 16 App Router, TypeScript, React 19, Postgres/Drizzle, existing `fetch`, AES-GCM helpers, Zod, Vitest.

**Spec:** [GitLab integration design](../specs/2026-11-06-gitlab-integration-design.md).

## Global Constraints

- Support GitLab.com and one self-managed instance per workspace.
- Self-managed hosts must be publicly reachable HTTPS; private-network-only instances are out of scope.
- Existing GitHub connections, routes, and repo JSON without a provider remain valid as GitHub.
- GitLab access/refresh tokens and instance OAuth client secrets are encrypted at rest and never returned to the browser.
- Organization admins configure workspace OAuth. Members authorize their own GitLab accounts.
- Manual generation uses the initiating member's connection; scheduled generation uses the project creator's connection.
- Scope GitLab reads narrowly, serialize rotating refresh-token use, cap requests/pagination, reject redirects, and apply timeouts.
- No GitLab SDK dependency; reuse fetch, AES-GCM, rate limits, tests, and current activity types.
- Preserve pre-existing user changes, including `release/config.json`; no production migration, commit, or push without explicit request.

## Review Focus

- Legacy repo JSON without `provider`: continues using GitHub and needs no backfill.
- Workspace/user mismatch: GitLab tokens, repos, and instance config remain scoped to their owner and member.
- OAuth callback replay or wrong user/workspace: state binding rejects the callback and secrets are never leaked.
- Concurrent refresh-token requests: only one refresh consumes the rotating token; other requests use the persisted replacement or return a reconnect error.
- Host changes/removal: reject changes while GitLab repo references exist; preserve historical logs and snapshots.

## Implementation Notes

- Test fixture hostnames must be reserved test domains and all GitLab API/OAuth calls stubbed; no customer or public GitLab endpoint is contacted by tests.
- URL validation must reject local/private IP targets and redirects at request time. If robust DNS-rebinding defense cannot be implemented for hostname resolution, constrain self-managed URLs to public DNS and verify every resolved address before connecting; document the operational limitation.
- Existing `.env.local` includes the GitHub OAuth variables. GitLab OAuth is configured per workspace in the application, not by adding required deployment-wide GitLab secrets.
